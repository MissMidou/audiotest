# Research: 微信扫码听音频二维码

**Phase 0 产出** | 用于支撑 plan 中的技术选型与契约设计。

---

## 1. 微信内置浏览器对 H5 音频与格式的支持

**Decision**: 使用 HTML5 `<audio>` 播放；优先支持 FLAC，在无法播放时提供明确提示或备选格式说明。

**Rationale**:
- 微信内置浏览器基于系统 WebView，对 `<audio>` 及常见格式（MP3、部分机型 FLAC）支持因系统/版本而异。
- Spec 明确示例为 `.flac`，故默认交付 FLAC；若目标环境不支持，可在 quickstart 或部署说明中建议“转 MP3 后替换”或后续增加构建时转码步骤。
- 不引入第三方播放器 SDK，保持静态页、无依赖，兼容性由实际真机扫码验证。

**Alternatives considered**:
- 仅 MP3：兼容最好，但 spec 示例为 flac，故保留 flac 为首选。
- 服务端转码：增加复杂度和托管要求，与“纯静态”约束冲突，暂不采用。

## 2. 目录数据来源：构建时生成 vs 运行时接口

**Decision**: 构建时生成。构建脚本扫描指定文件夹，生成目录清单（如 `manifest.json` 或内联到 `index.html`），静态页加载该清单渲染列表。

**Rationale**:
- Spec 要求“本方案交付可部署的 H5 目录页及音频托管方式”，且无“动态增删曲目”需求，构建时固定列表即可。
- 纯静态无后端，部署简单、无运维成本，符合“长期有效、仅公网”的假设。
- 清单结构在 data-model 与 contracts 中约定。

**Alternatives considered**:
- 运行时从服务器拉列表：需要后端或托管端 API，与当前“静态站点”方案不符，不采用。
- 纯手写 HTML 列表：可工作，但不利于多文件、多目录复用；脚本生成更可维护。

---

## 3. 二维彩虹与二维码生成

**Decision**: 不集成二维彩虹 API；交付物中提供“部署后如何将 H5 URL 填入二维彩虹生成二维码”的步骤说明（见 quickstart）。

**Rationale**:
- Spec 明确“使用二维彩虹生成标准二维码”，其能力为“用户提供 URL → 生成可微信扫描的二维码”，无需本方案实现二维码图形生成。
- 本方案仅需产出**可公网访问的 H5 页面 URL**，用户自行在二维彩虹网站填写该 URL 即可获得二维码，避免 API Key、计费与依赖。

**Alternatives considered**:
- 集成二维码生成库（如 qrcode.js）在构建阶段生成图片：与“二维彩虹生成”的约定不一致，且 spec 未要求本方案输出二维码图片文件，不采用。
- 调用二维彩虹 API：增加配置与网络依赖，非必需，不采用。

---

## 4. 静态托管与公网部署

**Decision**: 不绑定具体托管商；交付物为“可部署的静态目录”（如 `dist/`），支持任意支持静态托管的平台（GitHub Pages、Netlify、Vercel、自建 Nginx 等）。

**Rationale**:
- Spec 仅要求“公网可访问的 URL”；用户可自行选择托管与域名。
- quickstart 中以 1–2 种常见方式（如 GitHub Pages + 示例）说明部署步骤，其余平台用户可类比操作。

**Alternatives considered**:
- 仅支持某一家：会限制用户选择，不采用。
- 内置部署脚本（如 gh-pages）：可选放在 tasks 中，不在 research 强制约定。

---

## 5. 构建脚本语言：Python vs Node

**Decision**: 优先 Python 3.10+；若仓库已统一使用 Node，可改为 Node 18+ 脚本。在 data-model / quickstart 中按一种实现描述，另一实现视为等价替代。

**Rationale**:
- 构建逻辑简单：遍历文件夹、过滤音频扩展名、生成 manifest 或 HTML 片段、复制文件；Python 与 Node 均能短平快实现。
- 与“无框架、纯静态”一致，不引入重型构建工具（如 Webpack）除非后续有需求。

**Alternatives considered**:
- 使用 Vite/Webpack 等：对单页静态+列表而言过重，暂不采用。
- 仅手写 HTML 不写脚本：不利于多文件与重复构建，不采用。

---

## 6. Loading 与超时（FR-007）

**Decision**: 前端在加载页面与音频列表时显示 loading 状态；若在约定时间（如 15 秒）内未加载成功（页面或列表数据），展示错误提示（如“加载失败，请检查网络”），不无限等待。

**Rationale**:
- 与 spec 中 FR-007、Edge Cases 一致；实现为 JS 逻辑：请求 manifest 或解析内联数据时设超时与 catch，超时或失败则隐藏 loading、显示错误文案。
- 具体秒数可在实现时定为 10–15 秒，并在 UI 或 quickstart 中说明。

**Alternatives considered**:
- 不设超时：与 spec 要求不符，不采用。
- 仅服务端超时：无服务端，由前端实现即可。

---

## 7. 目录为空与全部不可用（Edge Case）

**Decision**: 若构建时扫描到的音频列表为空，构建脚本应报错或警告，避免部署“空目录页”；运行时若列表为空或全部加载失败，前端展示“暂无可播放音频”类提示，不白屏。

**Rationale**:
- Spec Edge Cases 明确“目录为空或全部文件不可用时，页面应展示明确提示”；构建时发现为空则提前失败，避免误导。
- 运行时列表为空（如 manifest 为空数组）时，不渲染播放列表，仅显示提示文案。

## Summary Table

| 主题               | 决策概要                                           |
|--------------------|----------------------------------------------------|
| 播放格式/载体      | HTML5 `<audio>`，优先 FLAC，不引入第三方播放器     |
| 目录数据           | 构建时生成 manifest 或内联列表，静态加载           |
| 二维码             | 不集成生成逻辑；文档说明用二维彩虹 + H5 URL 生成   |
| 托管               | 任意静态托管，quickstart 示例 1–2 种                |
| 构建脚本           | Python 3.10+ 或 Node 18+，二选一即可              |
| Loading/超时       | 前端 10–15 秒超时 + 错误提示                       |
| 空目录             | 构建时报错/警告；运行时展示“暂无可播放音频”       |
